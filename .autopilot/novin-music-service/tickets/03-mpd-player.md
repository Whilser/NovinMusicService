# 03 — MPD-клиент и управление воспроизведением

**Требования:** R05, R06, R12, R18, R19, R21i, R24i, G01

## Что должно заработать

Backend подключается к MPD на `novin`, проверяет соединение, возвращает статус, управляет транспортом и заполняет только временную очередь URI выбранных треков подряд либо случайно. Сохранённые плейлисты MPD не затрагиваются.

## Из брифа, дословно

> «воспроизводить эту музыку через MPD (установлен на том же сервере)»
> «настроек mpd»
> «прослушивание подряд или в случайном порядке»
> «плейлисты должны создаваться только внутри собственного музыкального сервиса, не трогая базу данных mpd»

## Разделы спецификации

Истории 14–20; MPD; HTTP API; контракт `mpd`.

## Критерии приёмки

- [ ] TCP parser корректно читает greeting, `key: value`, ACK и многострочные ответы с таймаутом
- [ ] Необязательный `MPD_PASSWORD` применяется без сохранения/возврата; host/port/uri_prefix берутся из несекретных настроек
- [ ] status и команды play/pause/previous/next/seek/volume работают через разрешённый whitelist
- [ ] `play_uris` безопасно кодирует пути, сохраняет порядок или перемешивает весь набор, управляет только текущей очередью
- [ ] Любые команды сохранённых плейлистов MPD отсутствуют и отклоняются
- [ ] API возвращает offline-состояние без падения каталога и фактический MPD status после команд
- [ ] Тесты используют fake MPD TCP server и доказывают отсутствие playlist persistence-команд
